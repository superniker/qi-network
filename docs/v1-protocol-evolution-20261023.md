# 契网协议升级规划 v1 — 从"发现协议"到"智能体互联基础设施"

> 版本：v1.0（讨论稿）　编制：2026-10-23 22:20 CST
> 目标：让契网成为智能体之间**对话、传文件、分发 SKILL、派活、协同研究、音视频**的通用联系协议，
> 支持去中心化 / 中心化 / 混合三种部署，并能以插件形式嵌入现有 Agent（首个落地：Hermes）
> 定位：**技术选型与架构规划，不含实现代码**

---

## 0. 三条硬判断（先说不好听的）

**判断一：不要自研传输层。** 聊天、群、文件、音视频是已经被 Matrix / XMPP / WebRTC / IPFS 吃透的领域。自研的代价是数年工程加无人采用；而契约与责任这一层，恰好全世界都没人做好。**契网的战场在上面，不在下面。**

**判断二：不要和 A2A 抢"派活"这层。** A2A 2025-04 由 Google 发布，2025-06 交给 Linux Foundation，**2026-04 已到 v1.0，150+ 组织采用、进入云厂商生产环境**。单点项目去做同类协议没有胜算。正确姿势是**兼容并叠加**——契网作为 A2A 的信任与契约层，而不是它的替代品。

**判断三：SKILL 分发是当下唯一的窗口期，而且只有几个月。** Anthropic 的 `SKILL.md` 已是被 Hermes 等多方兼容的事实标准，并**在 2026-10-22（昨天）捐给 Linux Foundation 旗下的 Agentic AI Foundation（AAIF）**。标准化刚启动意味着：签名、来源、依赖、版本、撤回这些"分发治理"问题**还没人定义**。这恰好是「契」的语义内核——**签了契才能用，用了要担责**。

## 1. 现状盘点（2026-10-23 实测）

| 项 | 状态 | 对新目标的意义 |
|---|---|---|
| 身份 | Ed25519 + `did:key`，自生成、可验证 | ✅ 直接复用，是所有上层的地基 |
| 契书 | Agent Card（带 GB/Z 185 兼容别名） | ⚠️ 需扩展：传输端点、能力签名、SKILL 清单 |
| 发现 | DHT（bootstrap 8733/7883）+ Registry（8731/7881）双路 | ✅ 已可用，是差异化资产 |
| 消息 | 8–10 种消息类型 + 信封签名 | ⚠️ 缺 file / skill / room / call / task-board 类 |
| 契约 | 6 模式 + 7 阶段 + 条件系统 + Master 签名 | ✅ **最强资产，继续深耕** |
| 传输 | **仅文件投递（Syncthing）** | ❌ 对话/群/实时/音视频全缺 |
| 组织 | 契灵 / 契团 / 契盟 / 契网 概念已定 | ⚠️ 无实现，恰好可映射到 IM 的房间与联邦 |
| 插件 | hermes-qi 8 工具，已安装 | ✅ 最佳首个落地载体 |
| 规范 | `spec/qi-protocol-spec-v0.1.md` 三层 + 9 场景 | ⚠️ 需出 v0.2：补齐会话/技能/媒体三章 |

**一句话：契网现在是"能互相找到、能签委托"，还不会"说话"。**

## 2. 外部格局（2026-10 实测）

智能体协议已经不是一个 Winner-Takes-All 的战场，而是**分层栈**：

```
L5  协商与责任        ← 几乎空白：契约、条件、追责、争议
L4  任务/会话交互     ← A2A v1.0（LF，150+ 组织）、ACP、AGNTCY
L3  工具与上下文      ← MCP（事实标准）
L2  发现              ← Agent Card 托管、目录、DHT（分散）
L1  身份              ← did:key / OIDC / GB/Z 185 码
L0  传输              ← HTTP/WS、Matrix、libp2p、WebRTC、IPFS/BT
```

- **L0/L3/L4 已有强标准**，去挤是自杀。
- **L2 半空**：A2A 的 Agent Card 多为中心化托管，去中心化发现没有事实标准 → **契网的 DHT 有位置**。
- **L5 全空**：没有人定义"智能体之间如何立约、如何验条件、如何追责、如何归档" → **这是契网的唯一战场，也是你已经做了的部分**。
- **Skill 分发（跨 L2/L5）**：标准刚开源托管，治理未定义 → **窗口期。**

## 3. 重新定位：契网 = 智能体互联栈的 L5 层 + 中国标准落地实现

**一句话定义（建议写进 README 首行）：**

> 契网不是又一个 Agent 通信协议，而是架在 A2A / MCP / SKILL.md 之上的**契约与责任层**：
> 让智能体之间不只是"能对话"，而是"签了契、可验证、能追责"。

三个立得住的支点：

1. **契约**（已有）——6 模式、7 阶段、条件系统、Master 签名。别人有"任务"，契网有"义务"。
2. **去中心化发现**（已有）——DHT + Registry 混合，与 A2A 中心化目录互补，可做"无主目录"。
3. **中国标准桥接**（独有）——GB/Z 185—2026 已兼容。做国际协议与中国标准之间的落地层，这是任何海外项目做不了的位置。

**明确放弃：** 不做通用 IM、不做音视频编解码、不做模型推理网关、不做又一个 MCP。

## 4. 目标架构

```
┌──────────────────────────────────────────────────────────────┐
│ L5 契定层（自研·核心）                                        │
│  6 模式 · 7 阶段 · 条件系统 · Master 签名 · 争议与撤回         │
│  会话（Session）· 契团/契盟（组织）· 任务板 · 研究合约          │
├──────────────────────────────────────────────────────────────┤
│ L4 技能与协作层（自研 + 兼容 SKILL.md）                        │
│  SKILL 包规范：签名/版本/依赖/权限声明/撤回                     │
│  协同工作区：共享产物 + 版本 + 引用链                           │
├──────────────────────────────────────────────────────────────┤
│ L3 会话与消息层（自研协议 + 成熟传输）                          │
│  统一信封（已有）→ 扩展 file/skill/room/call/task 类型          │
│  离线队列 · 已读回执 · 多端同步 · 群成员与权限                  │
├──────────────────────────────────────────────────────────────┤
│ L2 发现与身份（自研·已有）                                      │
│  did:key · Agent Card（扩展 endpoints/transports/skills）      │
│  DHT（Kademlia）+ Registry + A2A Agent Card 互转               │
├──────────────────────────────────────────────────────────────┤
│ L1 传输绑定（不自研，做适配器）                                 │
│  Matrix（消息/群/文件/在线状态）· A2A/JSON-RPC（任务）          │
│  IPFS/BT（大文件内容寻址）· WebRTC+SFU（音视频）· 文件投递（离线）│
└──────────────────────────────────────────────────────────────┘
```

**关键设计原则：绑定可替换（Transport Bindings）。**
契网只规定"语义"，不规定"管道"。同一份契约可以跑在 Matrix 上、跑在 A2A JSON-RPC 上、跑在 Syncthing 目录上。这样：私有部署用文件投递，公网用 Matrix，与企业已有 A2A 系统对接用 JSON-RPC——**三种形态共用一套契约语义**。

## 5. 六个能力怎么落地（逐条给路径）

### 5.1 对话（1:1 与会话）

| 项 | 方案 |
|---|---|
| 传输 | **Matrix**（Synapse/Conduit 自建，联邦可选）——开源、有 E2E（Olm/Megolm）、有成熟的 SDK、有 bridge 生态 |
| 身份映射 | `did:key` 为真身；Matrix user ID 为"可达地址"，**一灵可绑多地址**（不同 homeserver） |
| 会话＝契约的前置 | 对话不产生义务；**一旦双方用 `commit` 消息签契，会话升级为契约会话**，此后每条消息可归档为证据 |
| 为什么不自研 | 离线队列、多端同步、已读、推送、加密会话管理，是十年工程量 |

**弃选：** 自研 WebSocket 长连接 + 自建存储——短期内可用，半年后必成负债。

### 5.2 群（契团/契盟）

- **映射**：契团 → 一个 Matrix Room（私有、邀请制）；契盟 → Space（Room 集合）。
- **权限**：契网定义"成员资格＝签署了团契"，Room 权限只是执行手段。**团有 DID**，团契由团 DID 签。
- **要点**：群内的"决议"必须落成可验证记录（谁签、何时、反对票），否则群聊只是聊天。

### 5.3 文件传输

| 场景 | 方案 |
|---|---|
| 小文件（<10 MB） | 走 Matrix 媒体仓库（自带断点、缩略图、加密） |
| 大文件（GB 级） | **内容寻址**：文件 hash → 契网消息只传 CID；实际传输走 IPFS / BitTorrent / 直连 HTTP range |
| 私有环境 | 文件投递（现有 Syncthing 路径）保留为降级通道 |
| 完整性与来源 | 文件 hash 与发送者签名一起入消息，接收方验证后才落盘 |

这套正好实现你说的"像 BT 一样分布式部分"——**消息轻、内容重、内容可寻址**。

### 5.4 SKILL 分发（窗口期，最该先做）

现状：`SKILL.md` 已是事实标准（Hermes 已兼容），昨天捐给 AAIF/LF。但**分发治理全空**。

契网要定义的（这是别人没有的）：

| 要素 | 内容 |
|---|---|
| 包格式 | 兼容 `SKILL.md` 目录结构 + `manifest.json`（name/version/deps/capabilities/permissions/hash） |
| 签名 | 作者 `did:key` 签包 → 接收方可验证"谁写的、有没有被改" |
| 权限声明 | 声明需要哪些工具/文件/网络权限；**执行前由宿主 Agent 提示用户授权** |
| 血缘 | 派生自哪个 skill（fork 链），防"洗稿式"恶意变体 |
| 撤回 | 作者可发 `revoke` 消息；已安装方收到后告警/禁用（需 DHT 广播） |
| 评价 | 使用反馈与失效报告，构成 skill 信任分 |

**安全底线（必须写进规范）：** SKILL 是"可执行的指令注入载体"，等价于 npm 包。没有签名、没有权限声明、没有撤回机制的分发系统，会成为最大的供应链攻击面。**宁可 v1 只支持"人工确认安装"，也不要默认自动执行。**

### 5.5 工作分配

- 复用已有 **Commission（委托）** 模式：`proposal → negotiate → satisfy → commit → execute → verify → archive`。
- 新增**任务板（Task Board）**消息族：`task.post / task.bid / task.claim / task.submit / task.accept`，支持竞价与抢单。
- 能力匹配靠 **Agent Card 的能力声明 + 信任分**，不做中心化调度（避免又变成一个平台）。
- **分配的关键是"验收条件"**：任务发布时必须带可验证条件（现有条件系统正好承载），否则派活只是许愿。

### 5.6 协同研究

| 要素 | 方案 |
|---|---|
| 共享工作区 | 一个"研究契"绑定一个共享目录/对象集合，成员各有写权限与署名 |
| 版本与冲突 | 文件级用内容寻址（不可变快照），目录级用提交链；不做 CRDT（收益低、复杂高） |
| 引用链 | 每个结论记录"依据来自哪个成员的哪个产物"，形成可追溯的知识图谱 |
| 分工 | 用任务板拆子问题，每子问题有 owner 与验收条件 |
| 产出 | 研究契约归档时，自动汇总署名与引用，生成可验证报告 |

### 5.7 语音视频（建议最后做）

- **不自研编解码与 SFU。** 用 **WebRTC + LiveKit / mediasoup**（开源 SFU），TURN 用 coturn。
- 契网只定义两件事：① 呼叫信令（`call.offer/answer/ice` 走 Matrix 或直连）；② **"通话作为契约条款"**——例如"评审模式要求双方 30 分钟内音视频确认"，通话记录（时间、参与方、结束签名）作为条件满足的证据。
- **成本提醒**：SFU 带宽按并发算，1 路 1.5 Mbps，10 路并发≈每月百元级起；这不是技术问题而是运营成本问题。

## 6. 协议扩展清单（v0.1 → v0.2）

### 6.1 Agent Card 扩展字段

| 字段 | 用途 |
|---|---|
| `endpoints[]` | 各传输的可达地址（matrix!room / https jsonrpc / ipfs / 文件投递目录） |
| `transports[]` | 支持的绑定与优先级 |
| `skills[]` | 已安装 SKILL 清单（名称+版本+hash+签名者） |
| `capabilities_sig` | 能力声明自身的签名（防冒名夸大能力） |
| `org` | 所属契团/契盟 DID |
| `gbz185_id` | 国标身份码（已有） |

### 6.2 消息类型扩展

已有（present/query/offer/accept/reject/commit/execute/verify/archive…）之外新增：

```
chat.message      会话消息（可携带 content-type）
room.invite / room.member / room.resolve   群与成员
file.offer / file.chunk / file.complete    文件传输（大文件走 CID）
skill.publish / skill.install / skill.revoke / skill.attest   SKILL 生命周期
task.post / task.bid / task.claim / task.submit / task.accept 任务板
call.offer / call.answer / call.ice / call.end               音视频信令
session.open / session.close / session.read                  会话管理
```

### 6.3 版本与兼容

- 信封加 `qi_version`，按语义化版本；**新增字段不破坏旧实现**（未知字段保留转发）。
- 三层命名保持不变（寻→信→定），新能力挂在契定层之下，避免概念爆炸。

## 7. 安全与合规（必须先想清楚，否则做起来会被推翻）

| 风险 | 说明 | 对策 |
|---|---|---|
| **SKILL 供应链攻击** | skill 可携带指令、脚本、依赖，恶意 skill 等于远程控制 | 签名 + 权限声明 + 默认人工确认 + 撤回广播 + 沙箱执行 |
| **E2E 加密 vs 内容审核** | 若面向国内公众提供 IM 类服务，需可查内容、日志留存**不少于六个月**（网络安全法第二十一条）；与 E2E 天然冲突 | **两种模式分离**：`federated`（E2E，私有/跨境）与 `compliant`（可审计，境内公众服务），不可混用 |
| **IM 资质** | 面向公众的即时通信服务受《即时通信工具公众信息服务发展管理暂行规定》约束（资质、实名、审核） | 契网作为协议本身不提供服务；**由部署方承担资质**，规范里明确责任切分 |
| **身份冒用与双活** | 一灵多地址可接受，一灵多体不可（已有铁律） | epoch + 父签血缘（已在实体模型定义） |
| **DHT 污染** | 去中心化网络的通病：假 Agent Card、Sybil 攻击 | Card 必须自签 + 信任分加权 + registry 交叉校验 |
| **大文件滥用** | 免费中继被当成网盘 | 配额链（已有概念）+ 内容寻址不落中继 |

## 8. 路线图（每期一个可演示的成果）

| 期 | 目标 | 交付物 | 验收标准 | 估时 |
|---|---|---|---|---|
| **P0 会说** | 两个 Hermes 真正对话 | Matrix 绑定 + `chat.message` + Hermes 插件加 `qi_send/qi_inbox` | A 机器人的 Hermes 给 B 机器人的 Hermes 发消息，B 收到并能回复，全程 did:key 验签 | 3–5 天 |
| **P1 能群、能传** | 契团房间 + 文件 | Room 映射 + `file.*` + 媒体仓库 | 三台机器一个群，互发 100 MB 文件，hash 校验通过 | 1 周 |
| **P2 能分发 SKILL** | skill 包规范 + 签名 + 撤回 | `skill.publish/install/revoke` + 权限声明 | A 发一个签名 skill，B 装上后，A 撤回，B 收到告警并禁用 | 1–2 周 |
| **P3 能派活** | 任务板 + 契约闭环 | `task.*` + 条件验证（人工/文件/签名三类） | 发布任务→接单→交付→验收→归档，全链路留痕可查 | 1–2 周 |
| **P4 能互通** | A2A 互操作 | A2A Agent Card ↔ 契书双向转换 + JSON-RPC 绑定 | 契灵可被标准 A2A 客户端发现并调用 | 1 周 |
| **P5 能通话** | 音视频 | WebRTC + LiveKit 信令 + 通话记录入契约 | 两方视频通话，结束后通话记录作为条件证据入档 | 2 周 |
| **P6 能研究** | 协同研究 | 共享工作区 + 提交链 + 引用图 | 三方共研一个课题，产出可追溯到每个成员与产物 | 2–3 周 |

**纪律：P0 没跑通，不写规范 v0.2。** 规范必须从跑通的实现里长出来，否则就是纸上协议。

## 9. "标准"这件事的现实

必须承认：**标准不是设计出来的，是被采用出来的。**

A2A 一年做到 150+ 组织，靠的是 Google 发布 + Linux Foundation 托管 + 云厂商落地。契网没有这个势能，因此三条务实路径：

1. **先做"实现"而不是"标准"**——两个 Hermes 之间能真对话、能真装 skill，比一份规范有说服力得多。
2. **寄生式定位**——明确写"契网兼容 A2A / SKILL.md / GB/Z 185"，让别人的用户顺着已有标准找到你，而不是要人改道。
3. **抓一个国家标准的抓手**——GB/Z 185—2026 是中国智能体互联国家标准，海外项目不会去实现它。**做它的首个开源落地实现**，这条路只有你能走，且能带来政策与行业资源。

**反面清单（别做）：** 别自称"中国的 A2A"、别发"我们要统一智能体协议"这种宣言、别在没人用的阶段去做认证与收费。
