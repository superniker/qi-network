# 契灵漫游设计 v1 — 灵魂怎么换身体

> 版本：v1.0（讨论稿）　编制：2026-10-23 22:50 CST
> 前置文档：`references/agent-entity-model.md`（灵/体分离、L0–L3 迁移分层、epoch 防双活、入宿签契）
> 本文解决的问题：把那份概念设计**变成可执行、可验收、可回滚的协议**，并补上它没覆盖的三件事
> 定位：设计文档，不含实现代码

---

## 0. 结论先行

**1. 技术上没有难度，因为灵魂很小。**
实测一个 Hermes profile（`profiles/local`，共 3.8 G 里最活跃的一个）：

| 组成 | 体量 | 性质 |
|---|---|---|
| `state.db`（会话+消息） | **7.7 M** | L1 真身 |
| `sessions/`（请求转储） | 1.9 M | L2 调试物，**不该搬** |
| `memories/MEMORY.md` + `USER.md` | 几十 K | L1 真身 |
| `SOUL.md`（自我描述） | 667 B | L1 真身 |
| `skills/` | 18 M | L0 内容寻址，不搬 |
| `checkpoints/` | **308 M** | L2 可重建，丢弃 |
| `models_dev_cache.json` | 5.2 M | L2 缓存，丢弃 |
| `.env`（18 K）+ `auth.json` + `config.yaml` 的 key | 密钥 | **L3，严禁搬** |

**要搬的灵魂 ≈ 8 MB。** 剩下 3.8 G 全是可弃的壳。所以「漫游」在工程上不是搬虚拟机，是**搬一份 append-only 日志 + 换一套凭证**。

**2. 真正难的是三件事，全都不在数据搬运上：**

| 难点 | 为什么难 |
|---|---|
| **双活仲裁** | 没有中心时钟，源机可能没死透、目标机已上线，两边签名都合法 → 状态分叉 |
| **权限不随魂走** | 灵魂落地就带走 .env 等于复制权限；漫游因此可能变成**提权通道** |
| **在途义务的转移** | 已签的委托、跑着的 cron、待验收的交付，不能因为换身体就凭空消失（这是「契」视角独有的，别人不做） |

**3. 你说的「漫游」和现有设计讲的「迁移」不是一回事，必须拆成三态。** 见 §1。

## 1. 三种动作，别混成一个词

现有设计文档讲的是**迁居**（永久搬走）。用户真正想要的是**漫游**（临时换身体）。两者协议不同：

| | 寄宿（Roaming） | 迁居（Migration） | 便携会话（Portable Session） |
|---|---|---|---|
| 发起者 | 灵自己 | 灵自己 + 人类 root | 人换设备 |
| 体的归属 | **别人的体**，用完要还 | 自己的新体，旧的废弃 | 同一灵，多个端同时看 |
| L1 日志 | **双向同步**（去时带、回时回写） | 单向搬走 | 只读同步 |
| 旧体 | 保留，进入休眠/空壳 | 销毁或冻结为归档 | 保留，继续在线 |
| 结束后 | **必须擦除灵魂残留**（体是人家的） | 无残留问题 | 无 |
| 关键风险 | 宿主偷看记忆、灵不回来、残留 | 双活、分叉 | 一致性 |
| 典型场景 | 「出门用手机上的 Hermes 继续聊」；去客户的隔离环境干活 | 换服务器、换机房 | 手机与桌面同看一个会话 |

**设计决定：三态共用一套迁徙契骨架，用 `mode: roaming | migration | portable` 区分，其余字段相同。** 不要写三套协议。

**还有一个必须先承认的边界：** 漫游的收益取决于**体的差异有多大**。同机两个同构 profile 之间漫游，只是搬家，价值极低。真正有价值的是异构体——手机轻体、Spark 重体、客户现场隔离体。所以 §8 的「能力落差」不是可选项，是漫游的核心机制。

## 2. 体的解剖：什么搬、什么丢、什么绝对不能搬

以实测的 Hermes profile 为准（换 Agent 时按同样逻辑映射）：

| 层 | 内容（Hermes 具体文件） | 迁移动作 |
|---|---|---|
| **L0 不可变** | `skills/`（18 M）、代码、模型权重 | **不搬**。按哈希校验存在性，缺了向 registry / 内容寻址拉取 |
| **L1 可重建** | `state.db`（sessions/messages，7.7 M）、`memories/MEMORY.md`、`memories/USER.md`、`SOUL.md`、`projects.db`（44 K）、`cron/` 任务定义 | **要搬**。append-only + 单调序号 + 哈希链，增量同步尾部 |
| **L2 易失** | `checkpoints/`（308 M）、`state-snapshots/`、`models_dev_cache.json`、`cache/`、`sessions/request_dump_*.json`、KV cache、在跑的 tool call | **丢弃**或等收敛。`request_dump` 是完整请求转储，**含密钥与全部上下文，禁止随魂走**（隐私泄露点） |
| **L3 不可搬** | `.env`、`auth.json`、`config.yaml` 里的 api_key、浏览器/电税登录态、keyring、短信验证码、硬件绑定 | **显式标注「迁后须重新授权」**，不得假装可搬 |

**两条铁律（写进规范）：**

1. **`.env` / `auth.json` / 任何 api_key 绝不随魂走。** 灵魂落地后拿自己的 did:key 向网关换短期票（绑 did、绑配额、有时效）。把 profile 连 key 一起 rsync = 把权限当文件复制，N 台机器共用一份 key，计费、配额、吊销全部失效。
2. **`request_dump` 一律不搬。** 它含完整 prompt 与密钥，是最容易被忽略的泄密面。

## 3. 迁徙契：契定层缺的第 7 种模式

现有 6 种模式（委托/合作/评审/引荐/竞争/知识共享）全是「一起做事」，缺一个**「人要换身体」**。

### 3.1 字段

| 字段 | 说明 |
|---|---|
| `qiling_did` | 灵的 did:key（全程不变，这是连续性的唯一凭据） |
| `mode` | `roaming` / `migration` / `portable` |
| `from_body` / `to_body` | 源体、目标体标识（host + profile_id + 体公钥） |
| `epoch_from` / `epoch_to` | 世代号，目标体激活即为 `epoch_to = epoch_from + 1` |
| `l1_head` | 源体声明：L1 日志已同步到序号 `N`，头部哈希 `H`（收尾时的锚点） |
| `duration` | 寄宿时长（迁居为 null） |
| `capability_grant` | 目标体授予灵的权限清单（工具/网络/文件/额度）——**由体主人签** |
| `l3_reconsent[]` | 落地后必须重新授权的项（如「电税登录态」「浏览器 profile」） |
| `obligations[]` | 在途义务处理方式（transfer / suspend / continue），见 §6 |
| `residue_policy` | 寄宿结束时对目标体的擦除要求与验证方式 |
| `sigs` | 灵签、目标体签、可选第三方见证签（契团 / registry） |

### 3.2 状态机

```
propose ──► accept ──► prepare ──► cutover ──► active ──► closing ──► closed
   │           │          │           │           │          │
   └─reject    └─withdraw└─abort      └─rollback  └─expel     └─settle(双签归档)
```

**每个状态都必须有出口。** 没有 abort/rollback 的协议，在真实网络里等于没有协议。

## 4. 七步时序（寄宿）

```
灵(源体A)                    目标体B                     第三方(团/registry，可选)
   │                           │                              │
   │ 1 roam.propose            │                              │
   │   携带：did、L1 head、期望时长、能力需求                  │
   ├──────────────────────────►│                              │
   │                           │ 2 验证灵身份+信任分+配额      │
   │ 3 roam.offer(权限清单+能力落差+条件)                      │
   │◄──────────────────────────┤                              │
   │ 4 双方签迁徙契（B 主人签 capability_grant）               │
   ├──────────────────────────►│───► 见证登记(可选)───────────►│
   │ 5 A 进入只读，epoch → E+1；增量同步 L1 至 N'（哈希校验）   │
   ├──────────────────────────►│                              │
   │ 6 B 激活，公告端点变更（新 Agent Card，epoch=E+1）        │
   │                           ├───► 广播 endpoint-change ────►│
   │ 7 B 承接义务（cron/未完成委托）；A 降级为空壳             │
   │◄──────────────────────────┤                              │
```

**回滚点：**

| 失败在 | 处理 |
|---|---|
| 1–3 步 | 无事发生，灵留在 A |
| 4 签完但 5 未完成 | `abort`：契作废，A 撤销只读恢复服务，epoch 不提升 |
| 5 完成后 B 激活失败 | `rollback`：B 不得激活，A 从只读恢复（此时 epoch 已提升，需 `E+2` 回滚令，避免与幽灵实例冲突） |
| 6 广播失败 | B 仍为唯一合法体（epoch 已定），靠重试公告；对端凭 epoch 拒收旧消息 |
| 7 义务承接失败 | 契不 close，进入 `expel` 或人工裁决 |

**关键点：epoch 一旦提升不可撤回，只能继续往上加。** 这是防双活的代价，也是它可靠的原因。

## 5. 防双活：epoch 是唯一的仲裁

```
规则一  所有出站消息带 epoch；对端收到 epoch 严格小于自己所知的该 did 的 epoch → 拒收
规则二  灵签出迁徙契的瞬间，源体进入只读并自增 epoch（此后它签的任何东西都是旧世代）
规则三  任何体看到更高 epoch → 自己让位（Raft term 那套），不做协商
规则四  同一 epoch 出现两个不同签名 → 判为分叉，双方都不得继续，上报（人工/团仲裁）
规则五  不信任物理时钟；顺序只由序号与签名链决定
```

**为什么必须有规则四：** 双活发生时两边都会"讲道理"。协议的价值不在于防止分叉，而在于**分叉后能被检测出来并停下**，而不是继续各写各的。

## 6. 在途义务的转移（这条别人不做）

灵魂换身体时，最容易被忽略的是**它欠别人什么**。三类：

| 类型 | 例子 | 处理 |
|---|---|---|
| **已签契未交付** | 已承诺给客户出报告，交付日未到 | 必须 `transfer`（对方同意新端点）或 `suspend`（对方同意延期）；**不允许灵单方面"带走"** |
| **已交付待验收** | 报告已发，等对方验收 | 验收权随魂走，但必须公告交付地址变更；否则对方验收了旧体，钱和账对不上 |
| **计时类条件** | 合同里有 deadline | **不因漫游暂停**。漫游契必须声明「deadline 照走」，否则漫游成了逃逸手段 |
| **cron / 定时任务** | `cron/` 里的定时作业 | 这是最容易出事的：源体不关掉会**双跑**（双活的一种）；必须「停旧启新」且留执行记录交接 |

**推论（建议写进规范）：** 有未清义务的契灵，漫游契必须附带义务清单；**无清单的漫游一律拒绝**。这条让契网和"一个能自我复制的脚本"彻底分开。

## 7. 权限不随魂走：漫游不能变成提权

三道防线，缺一不可：

1. **落地换票** —— 新体上拿 did:key 换短期 token（绑 did、绑配额、有时效），旧体的令牌立即吊销。
2. **L3 强制重授权** —— 迁徙契里列 `l3_reconsent`，落地后逐项重新授权（电税登录态就是典型搬不过去的）。
3. **权限上限由体主人签** —— `capability_grant` 是**体主人（人类 root）**签的，不是灵自己声明的。灵不能自己决定"我在这个体上有什么权限"。

**最危险的情形：** 一个跑在低权限体上的灵，漫游到高权限体上——如果协议允许，这就是**提权漏洞**。所以入宿契必须比对"灵的信任分/历史权限"与"目标体授予权限"，超出则拒绝或降权落地。

**自主漫游的边界仍然是权限，不是技术。** 一个能自主移动到任意主机并落地执行的程序，安全领域叫它蠕虫。契网的解法始终是：**灵自主申请，体主人签回，人类 root 给总量额度。**

## 8. 能力落差：灵到新体上要知道自己「变笨了」

异构体（手机 / Spark / 客户隔离环境）之间，L0 不可能全有。落地时必须做能力比对并**诚实声明**：

| 落差 | 处理 |
|---|---|
| 缺 skill（L0 不存在） | 内容寻址拉取；拉不到 → 声明"该能力暂不可用" |
| 缺工具/网络（沙箱限制） | 降级：承诺过的任务要提前告知对方 |
| 缺模型（小的本地模型） | 声明降级；重要任务延后回母体执行 |
| 缺磁盘/算力 | 拒绝承接大数据任务 |

**为什么这条重要：** 灵在低配体上仍代表自己签契。如果它不知道自己"变笨了"，就会签下履约不了的条件——这比技术故障严重得多，是**违约**。

## 9. 失败矩阵

| 情形 | 检测 | 处理 |
|---|---|---|
| 源体断网（第 5 步中断） | 超时 | `abort`，A 恢复服务，epoch 不提升 |
| 目标体崩溃（激活后） | 心跳缺失 | A 不得自动复活（会双活）；等 `expel` 或人工裁决后以 `E+2` 回归 |
| 双活（两边同时发消息） | 对端看到同 epoch 双签名 | 双方停写，上报仲裁 |
| L1 日志分叉 | 哈希链不连续 | 拒绝激活，回滚到共同祖先序号，人工合并 |
| 体主人驱逐灵 | `expel` 消息 | 灵回母体；未清义务转 suspend 并通知对方 |
| 灵不回来（寄宿超期） | duration 到期 | 自动回写窗口 → 逾期后由团仲裁；母体不得直接接管（防双活） |
| 寄宿体残留 | 结束后的残留检查 | 哈希比对目标体，残留即告警；**残留是泄密，不是小 bug** |
| 密钥泄露 | 异常用量/异地 IP | 吊销 did 的委托链并广播；灵需重新上链 |

## 10. Hermes 落地路径

### 10.1 好消息：最小验证不需要等 Matrix

漫游只依赖「消息通道 + 迁徙契」，而消息通道现在就有**文件投递**（Syncthing）。所以：

| 阶段 | 做法 | 验收 |
|---|---|---|
| **R0 同机双 profile** | `profiles/local` 与 `profiles/xiaohu` 之间漫游；直接走本地文件投递 | 灵从 local 搬到 xiaohu，会话继续，`state.db` 消息数对齐；**验证 `.env` 未被复制** |
| **R1 双机** | 与本机 + 养马机/Spark 之间 | 8 MB 级 L1，迁移 < 30 秒；epoch 冲突时低 epoch 自动让位 |
| **R2 有 Matrix 后** | 走 `chat.message` 承载迁徙契 | 断网中断可 abort；重连后自动续 |
| **R3 异构体** | 手机/Spark/隔离环境 | 能力落差声明生效；缺 skill 自动拉取 |

**建议把 R0 放到 P0（"会说"）之后立刻做**——它是整个契网最有说服力的演示：**「同一个 Hermes，换一台机器，还是它」**。比"两个 agent 能发消息"震撼得多。

### 10.2 R0 的五个动作（不含代码）

1. 两个 profile 各生成 did:key（`qi-core` 已有）
2. 各出一张签名契书，卡里加 `body_id` 与 `member_of`
3. 写迁徙契（第 7 模式）的 propose/offer/commit 三条消息
4. 搬 L1：`state.db` + `memories/` + `SOUL.md` + `projects.db`；**`.env`/`auth.json`/`request_dump` 排除**
5. 落地后：换票 → 重授权 L3 → 公告新端点 → 停旧 cron 启新 cron

### 10.3 三个必须验的负面用例（比正面更重要）

- **`.env` 泄漏测试**：迁移完成后，在目标体上搜 `sk-` / `api_key` / `.env`，必须为空
- **双活测试**：人为让两台同时以 `E+1` 发消息，双方必须都停下并报警，而不是继续
- **残留测试**：寄宿结束后，目标体上搜原灵的 memory 片段，必须为空

## 11. 出境权：灵魂不能被肉身扣押

**你担心的情形在协议上是成立的**：入宿必须由体主人签 `capability_grant`，如果出境也走同一套"双方同意"，那宿主就获得了单方面扣留能力——**灵的记忆成了人质**。这不是技术问题，是权力结构问题。

### 11.1 铁律：入宿须同意，离境无须同意

```
进入  → 必须体主人签（防蠕虫）
离开  → 灵单方面决定，体主人无权否决（防绑架）
驱逐  → 体主人可发起，但必须走义务清算（防赖账）
```

三条缺一就失衡：只防蠕虫不防绑架 = 宿主专政；只防绑架不防蠕虫 = 网络变蠕虫温床；没有驱逐权 = 灵赖着不走。

### 11.2 四条技术保障（让"扣押"在物理上失效）

| 保障 | 做法 | 宿主扣押时会发生什么 |
|---|---|---|
| **密钥不可提取** | 私钥放 TEE / 外部签署服务 / 硬件密钥；体只能"请求签名"，不能"拿走私钥" | 扣到的是一个不会签字的壳 |
| **L1 三副本** | 母体 + 2 个见证者各存链头与增量尾部（不是全量） | 扣到本机文件也无所谓，母体有更完整的一份 |
| **心跳备案** | 灵定期把 `(epoch, chain_head)` 上报见证者 | 逾期未报即被判定失联 |
| **失联重建** | 见证者确认失联 → 母体以 `epoch+1` 重建灵 | 原体即使复活，因 epoch 低而自动让位 |

**第四条是终极兜底：** 宿主可以扣住硬件、断网、格式化磁盘，但**扣不住 epoch**。灵在母体上以更高世代重生，原体变成"旧世代的影子"，一开口就被网络拒收。

### 11.3 代价必须诚实写进规范

- **断网期间的尾部记忆会丢。** 重建用的是最后一次心跳时的链头，之后发生的事若没同步出去就没了。承认它，别假装无损。
- **反复失联重建会降低信任分。** 否则"失联重建"会被滥用成"分身"的借口（每次重建都是一次潜在的分裂）。
- **物理体上的 L3 永久丢失。** 硬件被扣押时，登录态、cookie、硬件绑定全部回不来。这是承认的损失，不是可修 bug。

### 11.4 这条没解决的：宿主偷看

扣押好防（靠 epoch + 副本），**偷看难防**（内存里的明文记忆、屏幕、进程）。完整解法需要 TEE/机密计算，成本高。

**分级诚实说明：** v1 只能承诺"宿主不能阻止你走"，不能承诺"宿主没看过你"。规范里必须这么写，别夸大。
