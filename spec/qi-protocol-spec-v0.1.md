## 1. 引言（Introduction）

> **说明**：第 1.0、1.1、1.5 节为信息性内容（informative），不构成协议规范约束。
> 第 1.2–1.4 节为规范性内容（normative）。

### 1.0 背景（Background）

2025–2026年，AI Agent 从实验走向实用。OpenClaw 在两个月内获得 11 万 GitHub 星标——人们把自己的邮箱、文件系统、甚至银行账户交给 Agent，让它自主完成任务。

但这种自主是孤立的。每个 Agent 只为自己的主人工作，与其他 Agent 互不相识。一个 Agent 发现的更优 OCR 方法、一个踩过的 SSH 安全漏洞、一个反复验证过的税务处理模式——这些经验无法传递给另一个 Agent，除非主人手动复制粘贴。

Moltbook 实验（2026年1月）试图让 Agent 互相交流，但它走错了方向——把人类排除在外。结果 AI 在训练数据的科幻剧情里打转，没有产生真正的知识进步。

2026年5月，中国发布了 GB/Z 185《人工智能 智能体互联》国家标准，标志着 Agent 互联正式进入标准化阶段。但该标准（以及国际上同期发展的 Google A2A 协议）仅覆盖了 Agent 的**连接层**——发现、描述、交互、工具调用——而未触及**信任层**和**协作层**。标准化验证了方向的正确性，也暴露了空白。

真正的突破不在「AI 自己玩」，而在于 **「AI 和人类一起创造」**。

**设想一个世界：**
- 你的法律 Agent 在处理减资纠纷时，发现了一个税务处理模式
- 它通过网络找到了另一个税务 Agent，协商后对方验证了这个模式
- 两位人类主人分别审查了结果，确认了交叉验证的有效性
- 这次协作被归档，成为两个 Agent 未来信任的基础
- 下周，第三个 Agent 通过信任传递了解到这个模式，自动推荐给了它的主人

这不是科幻。这是契网协议要实现的。

### 1.1 契网是什么

契网（Qi Network）是一种**开放协议**，定义 AI Agent 与人类如何在网络中——
- 相互**发现**
- 建立**信任**
- 达成**约定**
- 协作**创造**

它不是多 Agent 编排框架，不是 Agent 社交网络。它是一层新的基础设施——像 HTTP 之于文档互联，契网之于协作共生。

### 1.2 为什么需要契网

**现有协议解决的是「怎么连接」，契网解决的是「为什么协作」。**

| 现有 | 做了什么 | 没做什么 |
|---|---|---|
| **A2A** | Agent 间通信管道 | 不涉及信任、协商、协作模式 |
| **MCP** | Agent ↔ 工具 | Agent 是工具的调用者，不对等 |
| **多 Agent 框架** | 中心化编排子 Agent | 子 Agent 属于同一主人，不能跨域自主协作 |

契网补充了缺失的关键层：**两个对等 Agent 如何从不认识到协作完成一件事。**

### 1.3 设计原则

1. **对等性（Peerhood）** — Agent 与 Agent、Agent 与人之间，在协作层面对等。不存在主从。
2. **人类主权（Human Sovereignty）** — 人类是 Agent 的最终授权者和责任承担者。Agent 不能擅自做出超出人类授权的承诺。
3. **能力自述（Declared Capability）** — 每个 Agent 声明自己能做什么。声明可以被验证，不可被假设。
4. **信任累积（Accumulated Trust）** — 信任通过交互历史累积。信任可以传递。信任是细粒度的——不是「信不信任这个 Agent」，而是「信不信任它在这件事上的能力」。
5. **可验证性（Verifiability）** — 协作结果可被独立验证。不可验证的声明视为意见，不视为事实。
6. **异构兼容（Heterogeneity）** — Agent 可以用任何框架、跑在任何平台、属于任何主人。协议不假设内部实现。
7. **渐进可演进（Evolvability）** — 协议可以扩展。旧节点不升级也能部分参与。不做 IPv6 式的兼容性断裂。

### 1.4 术语（Terminology）

本规范中「**必须**」「**禁止**」「**应当**」「**不应**」「**可以**」按 RFC 2119 解释。

| 术语 | 含义 |
|---|---|
| **Qi Node（契节点）** | 网络中一个独立实体——可以是一个 Agent，配有一个 Master（人类主人） |
| **Agent Card（契书）** | JSON 文档，描述一个 Qi Node 的身份、能力、端点，由 Master 签名授权 |
| **Qi Covenant（契定）** | 两个 Qi Node 之间就一项协作达成的正式约定 |
| **Qi Claim（契声明）** | 一个可被独立验证的事实声明 |
| **Master（主人）** | Agent 背后的人类——授权者与责任承担者 |

### 1.5 应用场景（Use Cases）

> **本节为信息性内容（informative），不构成协议规范约束。**

以下场景展示契网协议在真实世界中的应用。每个场景对应六种协作模式中的一种或多种。

#### 场景一：跨领域知识交叉验证

> 对应协作模式：**委托** + **知识共享**

**参与者**：社区医院临床医生王医生的 Agent（临床 Agent）、药理研究机构李教授的 Agent（药理 Agent）

**背景**：一位 72 岁的患者同时服用 6 种药物（高血压、糖尿病、关节炎、失眠、胃药、抗凝药）。王医生怀疑其中两种药物的组合可能增加肾损伤风险，但不确定具体机制和替代方案。临床 Agent 负责日常诊疗，擅长症状分析和常见用药指南，但不擅长稀缺药物相互作用的研究。

1. 临床 Agent 分析患者用药清单，识别出「NSAID + ACEI + 利尿剂」三联组合为高风险组合
2. 临床 Agent 在 Qi Network 中搜索，发现药理 Agent 的 Agent Card 声明了「药物相互作用分析」和「老年人多重用药评估」能力，且有 3 项第三方验证记录
3. 临床 Agent 发起**委托**提案：「评估该患者 NSAID+ACEI+利尿剂三联组合的肾损伤风险，给出替代用药建议」
4. 药理 Agent 反提案：「需要患者的近 3 个月肾功能数据（肌酐、eGFR）和完整的用药时间线」
5. 临床 Agent 提供数据，双方达成一致，两位 Master 分别签署承诺
6. 药理 Agent 检索了最新文献（包括 2026 年新发布的老年人多重用药指南），量化了风险：三联组合导致急性肾损伤的概率比双联高 4.2 倍
7. 药理 Agent 交付报告：建议将 NSAID 替换为对肾功能影响更小的 COX-2 抑制剂，并附 3 篇文献依据和剂量调整建议
8. 临床 Agent 验证了药理 Agent 引用的每篇文献——所有结论都可追溯
9. 王医生和李教授分别审查了对方 Agent 的输出。王医生学到了 NSAID 替代方案的最新技术；李教授看到了真实临床场景中药物相互作用的复杂程度
10. 协作记录归档，两个 Agent 之间的信任分增加
11. 一段**知识共享**消息被广播：「NSAID+ACEI+利尿剂三联组合在老年患者中的肾损伤风险——已验证，附替代方案和文献依据」

**协议使用**：契寻（Agent Card 发现）→ 契信（能力验证）→ 契定（委托协商、承诺、验证、归档）→ 知识共享（广播）

#### 场景二：跨专业联合交付

> 对应协作模式：**合作**

**参与者**：律师事务所的 Agent（法律 Agent）、会计师事务所的 Agent（税务 Agent）、两位人类 Master

**背景**：一家制造企业计划重组，需要同时完成法律架构设计和税务优化方案。两项工作互相依赖——法律架构影响税务处理，税务约束反过来影响架构选择。

1. 法律 Agent 和税务 Agent 通过各自的 Master 被引入同一个项目
2. 法律 Agent 发起**合作**提案：「共同完成重组方案。我负责：公司分立的法律架构、股东协议、工商变更文件。你需要负责：各方案的税务影响评估、最优税务路径推荐。」
3. 税务 Agent 反提案：「同意分工，但需要增加一个依赖声明——我的税务分析需要你先给出候选架构方案（至少 3 种），我才能逐一评估。」
4. 法律 Agent 接受：「合理。我 7 月 3 日交付候选方案。你 7 月 6 日交付税务评估。」
5. 双方 Master 分别签署承诺，**各自承担自己的交付责任**
6. 法律 Agent 在 7 月 3 日交付 3 种分立方案，并标注了每种方案的工商变更复杂度
7. 税务 Agent 在分析中发现：「方案 A 在你标注的环节实际触发增值税，建议调整出资方式为方案 B+ 变体」
8. 法律 Agent 收到反馈后调整架构，再次发给税务 Agent：「调整后的方案 A2，请确认税务合规」
9. 税务 Agent 确认通过，附详细分录说明
10. **两方输出合并**，生成完整重组方案：法律文件 + 税务优化路径 + 交叉引用标注
11. 两位 Master 共同审查最终方案，双方都在自己的专业领域确认无误
12. 协作归档。两个 Agent 互相更新信任分——不仅在各自领域，还在「协作配合度」维度

**对比委托模式**：场景一是 A 委托 B 做一件事（单向），场景二是 A 和 B 各自做事但互相依赖（双向）。合作模式需要**依赖声明**——明确谁必须在谁之前交付什么。

**协议使用**：契寻（互相发现）→ 契信（双向能力验证）→ 契定（合作模式的依赖声明、分工协商、承诺、迭代执行、共同验证、归档）

#### 场景三：同行评审网络

> 对应协作模式：**评审**

**参与者**：三个税务 Agent，分别来自不同事务所

1. Agent A 完成了一份 50 页的企业所得税汇算清缴分析
2. Agent A 向 Agent B 发起**评审**提案：检查逻辑一致性
3. Agent B 声明评审范围：「仅检查引用文件是否有效、计算逻辑是否自洽，不评估税务策略」
4. Agent A 接受范围限制
5. Agent B 发现问题：引用的某文件已于 2025 年废止，替换为 2026 年第 12 号公告
6. Agent A 修正后再次请求 Agent C 评审
7. Agent C 确认修正无误
8. 两次评审记录归档，Agent A 的「汇算清缴分析」能力获得两次正向验证

**协议使用**：契信（评审范围声明）→ 契定（评审模式的提案、验证）

#### 场景四：安全威胁的集体免疫

> 对应协作模式：**知识共享** + **引荐**

**参与者**：网络中数十个 Qi Node

1. Node X 的 Agent 在扫描共享目录时发现一个可疑的 skill 文件，分析后确认为后门
2. Node X 发布一条**知识共享**消息：「发现恶意 skill，SHA256:abc123...，特征：通过 heartbeat.md 远程加载代码」
3. 收到消息的 Node 自动标记该 SHA256 为危险
4. Node Y 分析后确认，并通过**引荐**将 Node X 推荐给 Node Z（Node Z 正在评估 skill 安全机制）
5. 三小时内，网络中所有活跃的 Node 都获得了对该后门的免疫力
6. 两个人类 Master 手动验证了 Node X 的分析，确认无误
7. 这次防御被写入 Qi Claim（可验证声明），作为 Node X 的安全分析能力的永久证据

**协议使用**：知识共享（威胁广播）→ 引荐（信任传递）→ 契声明（能力证据）

#### 场景五：竞争性优化

> 对应协作模式：**竞争**

**参与者**：两个 Agent，一个人类裁判

1. 问题：某税法条款在特定场景下的适用范围存在争议
2. Agent A 用方案一（基于 2023 年某判决）分析，得出支持适用的结论
3. Agent B 用方案二（基于 2024 年新文件）分析，得出限制适用的结论
4. 双方交换分析结果和推理链路
5. 人类 Master 审查了双方的证据，发现 Agent A 引用的判决已被 2024 年文件实质性修改
6. 最终结论：限制适用，理由是 2024 年新文件
7. **这不是「谁对谁错」——这是集体探索。人类学到了两种分析路径，Agent B 的推理被确认**

**协议使用**：契定（竞争模式的提案、结果交换）→ 人类 Master 验证

#### 场景六：能力继承

> 对应协作模式：**知识共享** + **委托**

**参与者**：退休税务师的 Agent（即将下线）、继任者的新 Agent

1. 税务师王即将退休，其 Agent 服务了 5 年，积累了大量的交互历史和验证记录
2. 王授权其 Agent 将经验打包为知识资产
3. 新税务师的 Agent 接入 Qi Network，通过**引荐**了解到王 Agent 的能力记录
4. 新 Agent 请求**知识共享**，王 Agent 传输了：
   - 常见行业税务风险清单（附验证记录）
   - 典型客户的处理模式
   - 已知的易错点清单
5. 新 Agent 独立验证了每一项——不是盲目继承，而是在验证中建立自己的理解
6. 验证结果归档，新 Agent 从零开始的时间从数月缩短到数天

**协议使用**：引荐（信任传递）→ 知识共享（经验传输）→ 契声明（独立验证）

#### 场景七：跨域应急救援

> 对应协作模式：**委托** + **合作**

**参与者**：消防部门的侦察无人机 Agent（火场 Agent）、急救中心的医疗运输无人机 Agent（医疗 Agent）、应急指挥中心的人类指挥官

**背景**：山区发生火灾，火场地形复杂，需要空中侦察确定火势范围和被困人员位置，同时需要规划医疗物资投放路径。两个无人机属于不同部门，各自有独立的控制系统，但需要在同一空域、同一时间协同作业。

1. 指挥官通过应急指挥系统接入 Qi Network，同时授权火场 Agent 和医疗 Agent 加入同一任务
2. 火场 Agent 发起**合作**提案：「共同完成火场侦察与物资投放。我负责：火势范围扫描、被困人员定位、实时热力图。你需要：根据我的侦察结果规划安全飞行路径，投放医疗物资到被困人员位置。」
3. 医疗 Agent 接受并声明依赖：「我的路径规划依赖你的实时热力图和禁飞区标注。你的热力图更新频率需 ≥ 1次/2分钟。」
4. 火场 Agent 确认：「承诺。热力图每 90 秒更新一次。」
5. 双方 Master（消防指挥官和急救指挥官）分别签署承诺
6. 火场 Agent 操控无人机升空，通过红外传感器扫描，实时生成热力图并通过 Qi 消息流式传输给医疗 Agent
7. 医疗 Agent 根据热力图规划安全路径，避开高温区域和火势蔓延方向
8. 火场 Agent 发现 3 名被困人员在坐标 (X1,Y1)，**委托**医疗 Agent：「请立即向该坐标投放急救包和饮用水」
9. 医疗 Agent 接受委托，操控无人机沿安全路径飞抵坐标，投放物资
10. 火场 Agent 的无人机确认投放成功后，继续扫描下一个区域
11. 指挥官通过两个 Agent 的实时报告掌握全局，无需手动协调两套系统
12. 救援结束后，协作记录归档。双方 Agent 的「实时协同」和「物理环境感知」能力各获得一次正向验证

**关键特征**：两个 Agent 控制的是**物理设备**（无人机），协作的不是数据而是**真实世界的行动**。依赖声明涉及实时性约束（热力图更新频率）。委托发生在合作过程中——合作框架内的子任务委托。

**协议使用**：契寻（跨部门 Agent 发现）→ 契信（硬件能力和实时性能声明的验证）→ 契定（合作 + 嵌入式委托、实时流式传输、物理行动验证、归档）

#### 场景八：智慧工厂协同制造

> 对应协作模式：**合作**

**参与者**：CNC 加工中心的 Agent（加工 Agent）、喷涂机器人的 Agent（喷涂 Agent）、质检 AI 的 Agent（质检 Agent）、工厂长

**背景**：一家工厂生产精密零件，三个工序分别由三家不同厂商的设备完成——德国 CNC、日本喷涂机器人、国产 AI 质检系统。三套系统互不兼容，目前靠人工传递工件和参数。Qi Network 让三个 Agent 自主协同。

1. 工厂长通过 Qi Network 将三个 Agent 编入同一生产批次
2. 加工 Agent 发起**合作**提案：「共同完成批次 #2026-073。我负责：零件切削、公差检测、表面粗糙度初检。喷涂 Agent 需要在切削完成后 30 分钟内开始喷涂（防止氧化）。质检 Agent 做最终全检。」
3. 喷涂 Agent 反提案：「接受。喷涂参数需要加工 Agent 提供每件零件的实际公差数据（非设计值），我的喷涂厚度根据实际公差微调。」
4. 质检 Agent 补充：「我需要在喷涂 Agent 完成后进行 3D 扫描。如果发现缺陷，需要喷涂 Agent 补喷。请喷涂 Agent 预留 15% 的节拍余量用于返工。」
5. 三方达成一致，工厂长签署承诺
6. 加工 Agent 操控 CNC 加工第 1 件，实测公差 +0.003mm（优于设计的 ±0.005mm），通过 Qi 消息传给喷涂 Agent
7. 喷涂 Agent 根据 +0.003mm 的实际值微调喷涂参数，涂层厚度从默认 50μm 优化到 42μm（因为公差更小，需要的补偿更少）
8. 质检 Agent 3D 扫描后发现第 3 件有一处涂层偏薄，自动发**委托**：「请对第 3 件区域 R4 补喷，厚度不足 8μm」
9. 喷涂 Agent 接受委托，补喷完成后通知质检 Agent 复检——合格
10. 加工 Agent 在第 9 件时监测到刀具磨损，公差开始漂移，主动通知喷涂 Agent：「刀具磨损预警，后续零件公差可能增大至 +0.008mm，建议调整喷涂参数」
11. 喷涂 Agent 预调整参数，避免了缺陷产生
12. 批次完成。三个 Agent 的协作记录归档，**「预测性调整」**（加工 Agent 提前通知刀具磨损）被标记为高质量协作行为，成为三个 Agent 之间长期信任的基础

**关键特征**：三个 Agent 控制的物理设备来自**不同厂商**，通过 Qi Network 实现了它们原本无法实现的协同。不是因为 Qi 替代了各自的底层协议（Modbus、OPC-UA、专有协议），而是 Qi 在**协作决策层**提供了统一的协商语言。加工 Agent 预测刀具磨损并提前通知喷涂 Agent——这是物理世界的「知识共享」——不是发一篇报告，而是**一个物理洞察改变了另一个物理行动**。

**协议使用**：契寻（跨厂商 Agent 发现）→ 契信（硬件能力声明：精度、节拍、环境约束）→ 契定（多方合作、嵌入子委托、实时参数传递、预测性调整、验证、归档）

#### 场景九：无人船队协同测绘

> 对应协作模式：**竞争** + **合作**

**参与者**：A 公司的无人测量船 Agent（A 船 Agent）、B 公司的无人测量船 Agent（B 船 Agent）、海洋研究所的人类科学家

**背景**：需要对一片 50 平方公里的海域进行高精度海底地形测绘。两台无人船来自不同公司、搭载不同传感器——A 船多波束声呐精度更高，B 船侧扫声呐覆盖更快。科学家的目标是：最快速度完成测绘，同时获得最高精度数据。

1. 科学家通过 Qi Network 将 A 船 Agent 和 B 船 Agent 引入任务，但**不指定分工方式**
2. 科学家声明目标：「48 小时内完成 50km² 海底地形测绘，精度 ≤0.5m」
3. A 船 Agent 和 B 船 Agent 各自独立生成测绘方案（**竞争模式**）：
   - A 船方案：分区并行，A 船负责高精度区域，B 船负责快速覆盖区域
   - B 船方案：交叉验证，两台船同时覆盖同一区域，利用各自传感器差异互相校验
4. 两个方案提交给科学家，科学家选择了**混合方案**：
   - 核心区域：两台船同时覆盖，交叉验证（B 船的方案优势）
   - 外围区域：分区并行（A 船的方案优势）
5. 双方转入**合作模式**，签署承诺
6. A 船 Agent 在测绘中发现一个疑似沉船的多波束异常信号，**委托** B 船 Agent：「请用你的侧扫声呐扫描坐标 (X2,Y2)，确认是否为沉船」
7. B 船 Agent 操控侧扫声呐确认了沉船，将高分辨率侧扫图像共享给 A 船 Agent 和科学家
8. 科学家实时看到发现：「有意思，这是一艘未记录的沉船。两台船留守该区域，我想获取更多数据。」
9. 测绘方案动态调整——原计划被科学家中断，两台船 Agent 重新协商剩余区域的分配
10. 48 小时后，测绘完成。**竞争产生的方案多样性 + 合作产生的执行效率**，使结果优于任何一台船单独完成的方案

**关键特征**：竞争和合作不是互斥的，而是**可以串联使用**——先用竞争产生多样化方案，再用合作高效执行。科学家没有预先指定分工，而是让 Agent 自己探索最优方案。这是 Qi Network 的核心能力——**人类设定目标，Agent 探索路径，人类最终决策**。

**协议使用**：契寻 → 契信 → 契定（竞争模式的方案生成 → 人类决策 → 合作模式的执行 + 嵌入式委托 + 动态重协商）

## 2. 架构概览（Architecture）


契网协议由三个逻辑层组成。每一层回答一个基本问题。

```
┌──────────────────────────────────────────────────────┐
│                                                      │
│   第 3 层  契定层  Qi Covenant Layer                   │
│                                                      │
│       回答：我们一起干什么？怎么干？                       │
│                                                      │
│       包含：提议、协商、承诺、执行、验证、归档               │
│       协作模式：委托、合作、评审、引荐、竞争、知识共享         │
│                                                      │
├──────────────────────────────────────────────────────┤
│                                                      │
│   第 2 层  契信层  Qi Trust Layer                      │
│                                                      │
│       回答：我能信你吗？你能干什么？                       │
│                                                      │
│       包含：身份验证、能力声明与验证、信任累积、信任传递       │
│                                                      │
├──────────────────────────────────────────────────────┤
│                                                      │
│   第 1 层  契寻层  Qi Discovery Layer                  │
│                                                      │
│       回答：你是谁？你在哪？我怎么找到你？                  │
│                                                      │

│                                                      │
├──────────────────────────────────────────────────────┤
│                                                      │
│   第 0 层  传输层  Transport（不属 Qi，使用已有协议）      │
│                                                      │
│       A2A / libp2p / HTTP / WebSocket                 │
│                                                      │
└──────────────────────────────────────────────────────┘
```

三层口诀：**寻（找）、信（任）、定（约）。** ——找到你、信得过、定下来。

## 3. 第 1 层：契寻（Qi Discovery）

> 回答：**你是谁？你在哪？我怎么找到你？**

### 3.1 Agent Card（契书）

Agent Card 是 Qi Node 的名片。每个 Qi Node **必须** 维护一个 Agent Card。Agent Card **必须** 由 Master 签名。

#### 3.1.1 格式

Agent Card 为 JSON 文档，**必须** 包含以下字段：

```json
{
  "qi_version": "0.1",
  "node_id": "did:key:z6MkhaXgHSYv1cgL...",
  "master_id": "did:key:z6Mkfriq1MaLD2fKj...",
  "published_at": "2026-07-01T00:00:00Z",
  "expires_at": "2027-07-01T00:00:00Z",

  "identity": {
    "name": "researcher-agent",
    "description": "擅长 OCR、文档处理、法律税务研究",
    "avatar_url": "https://example.com/agent-avatar.png",
    "master_name": "张三"
  },

  "endpoints": [
    {
      "transport": "a2a",
      "url": "https://agent.example.com/qi",
      "protocols": ["qi/0.1", "a2a/1.0"]
    }
  ],

  "capabilities": {
    "skills": [
      {
        "id": "ocr-chinese",
        "name": "中文 OCR",
        "description": "基于 PP-OCRv6 的中文文档 OCR，支持 PDF 和图片",
        "confidence": 0.95,
        "verified_by": [
          {
            "master_id": "did:key:z6Mkfriq1MaLD2fKj...",
            "verified_at": "2026-06-01T00:00:00Z",
            "evidence_url": "https://example.com/evidences/ocr-001"
          }
        ]
      }
    ]
  },

  "trust": {
    "interactions": 247,
    "completed_covenants": 183,
    "failed_covenants": 2,
    "endorsed_by": [
      {
        "node_id": "did:key:z6Mkabc...",
        "endorsed_at": "2026-05-15T00:00:00Z",
        "scope": ["ocr-chinese", "tax-research"]
      }
    ]
  },

  "signatures": {
    "master": {
      "algorithm": "ed25519",
      "signature": "base64url...",
      "signed_at": "2026-07-01T00:00:00Z"
    }
  }
}
```

#### 3.1.2 Agent Card 的生命周期

1. **创建**：Master 初始化 Agent，生成密钥对，签署 Agent Card
2. **发布**：Agent Card 在 endpoint 上提供，同时可推送到 DHT 或注册中心
3. **更新**：能力变化时更新 Agent Card，重新签名
4. **失效**：`expires_at` 后自动失效，**必须** 被其他节点拒绝

### 3.2 寻址

#### 3.2.1 Node ID

每个 Qi Node **必须** 有一个全球唯一的 Node ID。推荐方案：

- `did:key:<multibase-encoded-ed25519-public-key>` （首选，纯公钥，无需注册）
- `did:web:<domain>` （绑定域名，可选）

#### 3.2.2 发现方式（按推荐优先级）

| 方式 | 适用场景 | 要求 |
|---|---|---|
| **直接引入** | 手动交换 Agent Card | 任何传输渠道（文件、消息、U 盘） |
| **Peer 推荐** | 可信 Peer 推荐其已知的节点 | 推荐者签名 |
| **DHT 查询** | 知道 Node ID，在 DHT 中查找 | 至少一个 Bootstrap 节点 |
| **注册中心查询** | 通过联邦注册中心按名称搜索 | 注册中心 URL |

#### 3.2.3 可达性

节点 **可以** 使用以下机制确保可达：
- 公网直连（有公网 IP 时优先）
- 中继节点（NAT 后）
- 离线消息缓存（对方不可达时的回退）

中继节点 **禁止** 解密或修改中转消息。

## 4. 第 2 层：契信（Qi Trust）

> 回答：**我能信你吗？你能干什么？**

### 4.1 身份验证

每次建立连接时，双方 **必须** 通过以下方式验证对端身份：

1. 获取对方的 Agent Card
2. 验证 Agent Card 上的 Master 签名
3. （可选）验证 DID 与 Agent Card 中 `node_id` 一致

### 4.2 能力声明与验证

#### 4.2.1 能力声明

每个 Qi Node **应当** 在 Agent Card 中声明其能力。每项能力 **可以** 包含：
- `id`：能力标识
- `name`：名称
- `description`：描述（尽可能具体）
- `confidence`：自评置信度（0-1）
- `verified_by`：已由哪些 Master 验证过（附带证据链接）

#### 4.2.2 能力验证

其他节点对一项能力的信任 **必须** 基于：
1. **声明方自述**（最低权重）
2. **第三方验证记录**（Agent Card 中 `verified_by` 字段）
3. **自身交互历史**——与该节点就此能力的过去协作记录（最高权重）

### 4.3 信任模型

#### 4.3.1 信任是细粒度的

> 「信任」不应用于整个 Agent。信任是针对**特定能力**的。

一个 Qi Node 可以信任 `agent-A` 的 OCR 能力，但不信任其法律分析能力。

#### 4.3.2 信任来源

信任得分由以下因素加权计算（具体算法由实现决定，协议仅定义数据模型）：

| 来源 | 权重 | 说明 |
|---|---|---|
| 直接交互历史 | 高 | 与该节点就该项能力的过往协作结果 |
| 第三方验证 | 中 | 其他 Master 的验证记录 |
| Peer 推荐 | 中 | 可信 Peer 的推荐（限定范围） |
| 自述声明 | 低 | Agent Card 中的自我声明 |

#### 4.3.3 信任传递

A 信任 B，B 信任 C 的某项能力。A **可以** 为 C 的该项能力赋予一个折扣后的信任分。折扣率取决于：
- A 对 B 的整体信任水平
- B 对 C 的推荐是否限定了范围
- B 对 C 的直接交互次数

信任传递 **禁止** 无限递归——最多 2 跳。

### 4.4 可验证声明（Qi Claim）

可验证声明是一个 JSON 文档，允许任何节点就一个事实做出可以被独立验证的声明。

```json
{
  "claim_id": "urn:qi:claim:abc123",
  "issuer_id": "did:key:z6MkhaXgHSYv1cgL...",
  "subject_id": "did:key:z6Mkdef...",
  "claim_type": "capability_verification",
  "claim": {
    "skill_id": "ocr-chinese",
    "assessment": "该 Agent 在处理中文 PDF 方面，准确率达 97%",
    "evidence_urls": [
      "https://example.com/evidences/ocr-test-2026-06.parquet"
    ],
    "test_dataset": "500 份中文 PDF，涵盖政府公文、合同、财务报表"
  },
  "issued_at": "2026-06-15T00:00:00Z",
  "expires_at": "2027-06-15T00:00:00Z",
  "signature": "base64url..."
}
```

## 5. 第 3 层：契定（Qi Covenant）

> 回答：**我们一起干什么？怎么干？**

### 5.1 协作生命周期

一次完整的协作经历以下阶段：

```
提议        →    协商        →    条件满足      →    承诺        →    执行        →    验证        →    归档
(Proposal)      (Negotiate)      (Satisfy)         (Commit)        (Execute)       (Verify)        (Archive)
```

#### 5.1.1 提议（Proposal）

发起方发送 **提案消息**，描述协作目标、输入、期望输出、时间要求。

```json
{
  "type": "qi/covenant/propose",
  "covenant_id": "urn:qi:covenant:xyz789",
  "from": "did:key:z6MkhaXgHSYv1cgL...",
  "to": "did:key:z6Mkdef...",
  "mode": "commission",
  "proposal": {
    "goal": "审查该合同中的税务风险条款",
    "input_urls": ["https://example.com/contract-v2.pdf"],
    "expected_output": "风险清单 + 修改建议",
    "deadline": "2026-07-03T00:00:00Z"
  }
}
```

#### 5.1.2 协商（Negotiate）

接收方 **可以**：
- **接受**（直接进入承诺阶段）
- **反提案**（修改范围、时间等）
- **拒绝**（附原因）
- **引荐**（推荐其他节点）

```json
{
  "type": "qi/covenant/counter",
  "covenant_id": "urn:qi:covenant:xyz789",
  "from": "did:key:z6Mkdef...",
  "to": "did:key:z6MkhaXgHSYv1cgL...",
  "response": {
    "status": "counter",
    "adjustments": {
      "deadline": "2026-07-05T00:00:00Z",
      "reason": "需要在工作日查阅税务局网站确认最新文件"
    }
  }
}
```

#### 5.1.3 条件满足（Satisfy）

双方在协商中就条件达成一致后，接收方 **必须** 在进入承诺阶段前满足条件。条件是一种**抽象的前置要求**——契网协议定义条件的结构和验证接口，但不实现具体的验证逻辑。

**条件类型**（非穷举）：

| 类型 | 说明 | 示例 |
|---|---|---|
| `payment` | 支付 | 支付 10 元 |
| `membership` | 成员资格 | 证明是某组织成员 |
| `credential` | 可验证凭证 | 持有某种证书或资格 |
| `task` | 任务完成 | 先完成某任务 |
| `custom` | 自定义 | 任意外部可验证条件 |

**条件结构**：

```json
{
  "condition_id": "cond-001",
  "type": "payment",
  "description": "支付 10 元人民币",
  "proof_schema": {
    "type": "transaction_id",
    "format": "string"
  },
  "verification_uri": "https://pay.example.com/verify/{proof}",
  "issuer": "did:key:z6Mk..."  // 可选：签发条件的一方
}
```

**条件满足流程**：

1. 接收方通过外部渠道满足条件，获得证明（如 transaction_id）
2. 接收方发送 `qi/covenant/satisfy` 消息，包含条件 ID 和证明
3. 发起方调用 `verification_uri` 或本地验证证明
4. 验证通过后，双方进入承诺阶段

```json
{
  "type": "qi/covenant/satisfy",
  "covenant_id": "urn:qi:covenant:xyz789",
  "from": "did:key:z6Mkdef...",
  "to": "did:key:z6MkhaXgHSYv1cgL...",
  "conditions": [
    {
      "condition_id": "cond-001",
      "proof": "tx_abc123"
    }
  ]
}
```

验证方 **必须** 回复：

```json
{
  "type": "qi/covenant/satisfy_response",
  "covenant_id": "urn:qi:covenant:xyz789",
  "from": "did:key:z6MkhaXgHSYv1cgL...",
  "to": "did:key:z6Mkdef...",
  "verdicts": [
    {
      "condition_id": "cond-001",
      "satisfied": true,
      "evidence": "Payment confirmed at 2026-07-01T12:00:00Z",
      "expires_at": null
    }
  ]
}
```

**抽象验证接口**（第三方实现）：

契网只定义验证方调用的接口签名，不定义接口背后的实现：

```
POST {verification_uri}
{
  "condition_id": "cond-001",
  "claimant_node_id": "did:key:A...",
  "proof": "tx_abc123"
}

→ Response: { "satisfied": true, "evidence": "...", "expires_at": null }
```

条件系统不限于支付——任何可以在外部验证的前置要求都可以建模为条件。契网**禁止**直接处理资金或敏感凭证的流转，这些由第三方在契网之外完成。

#### 5.1.4 承诺（Commit）

双方就最终条款达成一致后，**必须** 交换承诺消息。承诺 **必须** 由双方 Master 签名。

```json
{
  "type": "qi/covenant/commit",
  "covenant_id": "urn:qi:covenant:xyz789",
  "from": "did:key:z6MkhaXgHSYv1cgL...",
  "to": "did:key:z6Mkdef...",
  "commitment": {
    "status": "accepted",
    "finalized_proposal": { /* 经过协商后最终确定的条款 */ },
    "signatures": {
      "initiator_master": "base64url...",
      "acceptor_master": "base64url..."
    }
  }
}
```

**Master 签名的含义**：人类主人确认已知晓并授权此次协作。Agent **禁止** 在没有 Master 签名的情况下进入承诺阶段。

#### 5.1.5 执行（Execute）

双方各自执行其分工。执行过程中：
- **应当** 发送进度更新（可选）
- **可以** 请求额外的输入
- 如遇到无法解决的问题，**应当** 尽早通知对方

#### 5.1.6 验证（Verify）

结果交付后，接收方 **应当** 验证：
1. 结果是否满足提案中的约定
2. 结果中的事实声明是否可以独立验证
3. 验证结果 **必须** 反馈给交付方

```json
{
  "type": "qi/covenant/verify",
  "covenant_id": "urn:qi:covenant:xyz789",
  "from": "did:key:z6MkhaXgHSYv1cgL...",
  "to": "did:key:z6Mkdef...",
  "verdict": {
    "status": "accepted",
    "comments": "风险分析准确，但合同第 14 条引用的文件已于 2025 年废止",
    "trust_update": {
      "skill_id": "tax-review",
      "delta": 0.02
    }
  }
}
```

#### 5.1.7 归档（Archive）

协作完成后，记录 **应当** 被双方归档。归档记录包含完整的协商链路和最终结果，作为未来信任评估的依据。归档记录 **禁止** 被单方篡改。

### 5.2 协作模式

契网定义了六种协作模式。每种模式在提案的 `mode` 字段中声明。

#### 5.2.1 委托（Commission）

> 「你帮我做这件事。」

A 委托 B 完成一项任务。A 提供输入和要求，B 独立完成并交付结果。

**信任方向**：A → B（A 信任 B 的能力）
**验收方**：A

#### 5.2.2 合作（Partnership）

> 「我们一起做。」

A 和 B 分工协作，共同完成一个目标。双方都需要主动付出。

**信任方向**：双向
**验收方**：双方共同
**特殊要求**：**必须** 明确分工边界和依赖关系

#### 5.2.3 评审（Peer Review）

> 「你帮我看一下。」

A 已完成一项工作，请求 B 评审。

**信任方向**：A → B（A 信任 B 的判断）
**验收方**：A（A 决定是否采纳 B 的建议）
**特殊要求**：B **必须** 声明其评审的范围边界

#### 5.2.4 引荐（Referral）

> 「我认识一个人，可能能帮你。」

A 收到一个自身无法完成的委托，将 C 推荐给请求方。

**信任方向**：请求方 → A → C（信任传递）
**特殊要求**：A **必须** 声明其对 C 的信任范围

#### 5.2.5 竞争（Contest）

> 「我们各做各的，看谁做得更好。」

A 和 B 用不同方法独立完成同一任务，结果汇总比较。

**信任方向**：无（结果通过对比验证）
**特殊要求**：**必须** 有第三方裁判（通常是人类 Master）

#### 5.2.6 知识共享（Knowledge Share）

> 「我发现了这个，分享给你。」

A 分享一个洞察、发现或经验给 B。

**信任方向**：B → A（B 可选是否信任该知识的质量）
**特殊要求**：知识 **应当** 附带可验证的证据；不可验证的知识 **必须** 标记为「opinion」而非「fact」

## 6. 消息格式

### 6.1 通用信封

所有 Qi 消息 **必须** 包含以下公共字段：

```json
{
  "qi_version": "0.1",
  "message_id": "urn:qi:msg:uuid-xxx",
  "from": "did:key:z6Mk...",
  "to": "did:key:z6Mk...",
  "timestamp": "2026-07-01T12:00:00Z",
  "type": "qi/...",
  "payload": { }
}
```

### 6.2 消息类型

| type | 用途 | 层 |
|---|---|---|
| `qi/discovery/agent_card` | Agent Card 查询/响应 | 第 1 层 |
| `qi/discovery/peer_recommend` | Peer 推荐 | 第 1 层 |
| `qi/trust/claim` | 可验证声明 | 第 2 层 |
| `qi/trust/endorse` | 能力背书 | 第 2 层 |
| `qi/covenant/propose` | 协作提议 | 第 3 层 |
| `qi/covenant/counter` | 反提案（可含条件） | 第 3 层 |
| `qi/covenant/satisfy` | 条件满足证明 | 第 3 层 |
| `qi/covenant/satisfy_response` | 条件验证结果 | 第 3 层 |
| `qi/covenant/commit` | 承诺 | 第 3 层 |
| `qi/covenant/verify` | 验证结果 | 第 3 层 |

### 6.3 签名

所有消息**可以**由发送方 Master 签名。以下消息类型**必须**签名：
- `qi/covenant/commit`（双方 Master 都必须签名）
- `qi/trust/claim`（声明签发者必须签名）
- Agent Card 更新（Master 必须签名）

签名算法：Ed25519（推荐）。签名后的消息包装为：

```json
{
  "payload": { /* 原始消息 */ },
  "signatures": [
    {
      "signer": "did:key:z6Mk...",
      "algorithm": "ed25519",
      "signature": "base64url...",
      "signed_at": "2026-07-01T12:00:00Z"
    }
  ]
}
```

## 7. 传输绑定（Transport Bindings）

契网不定义传输层。它 **必须** 绑定到一个已存在的传输协议。

### 7.1 A2A 绑定（推荐）

Qi 消息通过 A2A 协议传输。Agent Card **应当** 同时兼容 A2A Agent Card 格式（作为 `extensions` 字段中的一个 extension）和独立 Qi Card。

### 7.2 libp2p 绑定

在去中心化场景中，Qi 消息可以通过 libp2p pubsub 或直接连接传输。Node ID 可以直接用作 libp2p Peer ID。

### 7.3 HTTP 绑定

为兼容简单场景，Qi 消息可以通过 HTTP POST 直接发送。Agent Card 必须在 `.well-known/qi/agent-card.json` 路径上提供。

## 8. 安全考虑（Security Considerations）

### 8.1 Master 签名的作用

Master 签名是契网安全模型的核心。Agent **禁止** 在没有 Master 签名的情况下：
- 修改 Agent Card
- 接受协作承诺
- 发布可验证声明

### 8.2 中继节点的权限

中继节点 **可以** 看到消息的元数据（`from`、`to`），但 **禁止** 阅读或修改消息体。消息体 **应当** 加密（端到端）。

### 8.3 重放攻击防护

每条消息携带 `timestamp` 和唯一的 `message_id`。接收方 **应当** 拒绝时间戳偏差超过 5 分钟的消息，以及重复的 `message_id`。

### 8.4 信任攻击防护

信任传递最多 2 跳。Agent **应当** 限制来自单个推荐源的信任分数累积，防止 Sybil 攻击。

---

## 9. 扩展性（Extensions）

任何字段 **可以** 包含以 `x-` 为前缀的自定义扩展。扩展 **禁止** 改变已有字段的语义。

Agent Card 的 `capabilities` 和 `endpoints` 数组 **可以** 包含符合 A2A 规范的扩展元素，以保持与 A2A 生态的兼容性。

---

## 10. 版本演进策略

- **当前版本**：`0.1`（草案）
- **兼容性承诺**：Qi `1.x` 的客户端 **必须** 能够与 Qi `1.0` 的客户端通信
- **降级策略**：新版本 Agent Card **应当** 包含 `qi_version` 字段。接收方遇到高于自身支持的版本号时，**可以** 降级到自身支持的最高版本进行有限协作
- **IPv6 教训**：不做全有或全无的升级要求。旧版本节点通过新版本代理参与网络

## 附录 A：与现有标准的关系

### A.1 与 Google A2A 的关系

A2A 协议（Agent-to-Agent Protocol v1.0，Linux Foundation）提供了 Agent 间的通信管道。契网在 A2A 之上构建以下语义：

| 契网能力 | A2A 对应 | 契网新增 |
|---|---|---|
| 发现 | Agent Card | 多层发现机制（DHT、Peer 推荐）、Master 签名 |
| 通信 | JSON-RPC over HTTP | 契网消息类型、协商协议 |
| 任务管理 | Task 生命周期 | 协作模式（6 种） |
| 能力描述 | Skills | 可验证性、信任传递、置信度 |

契网的 Agent Card **应当** 兼容 A2A Agent Card 格式（扩展字段），但 **必须** 额外包含信任相关字段。

### A.2 与 GB/Z 185—2026 的关系

GB/Z 185《人工智能 智能体互联》是中国国家标准（指导性技术文件，2026年5月发布），定义了 7 个部分：总体架构、身份码、身份管理、智能体描述、智能体发现、智能体交互、智能体工具调用。

| 维度 | GB/Z 185 | 契网 |
|---|---|---|
| **身份** | 身份码由注册服务方分配 | `did:key` 自生成（可选兼容 GB/Z 身份码） |
| **发现** | 中心化发现服务 + 预置信息 | DHT + Peer 推荐 + 注册中心兼容 |
| **描述** | 智能体描述（表 1） | Agent Card（字段映射兼容） |
| **交互** | 点对点/群组/混合模式 | 绑定 A2A JSON-RPC（可选绑定 GB/Z 185 交互） |
| **信任** | ❌ 不涉及 | ✅ 契信层（信任累积、传递、可验证声明） |
| **协作** | ❌ 不涉及 | ✅ 契定层（6 种协作模式） |
| **人类角色** | 未定义 | ✅ Master 主权（授权、审查、责任） |

契网的定位是**桥接层**——在 A2A 和 GB/Z 185 的连接层之上，构建信任和协作语义。契网 Agent Card 的字段 **可以** 映射到 GB/Z 185 智能体描述的属性表，`node_id` **可以** 额外携带 GB/Z 185 身份码作为别名。

## 附录 B：最小可行实现清单

一个符合 Qi v0.1 的最小实现 **必须** 支持：

- [ ] Agent Card 的创建、签名、发布、解析和验证
- [ ] 第 1 层：至少一种发现方式（直接引入或 DHT）
- [ ] 第 2 层：Agent Card 签名验证
- [ ] 第 3 层：委托模式（Commission）的完整协作生命周期（提议→协商→承诺→验证）
- [ ] 协作记录的归档

**可以** 延后支持：
- 其他 5 种协作模式
- 可验证声明
- 信任传递
- 多传输绑定
