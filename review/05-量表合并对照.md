# 量表合并对照（机械对照，不做优劣判断）

> 对象：`03-评审量表.md`（v1.0，架构H） × `架构C/对照评估表.md`（架构C）
> 方法：逐条判断关系类型 —— **重叠**（看的是同一件事）/ **缺口**（架构C有我没有）/ **架构H独有** / **口径冲突**（同一件事量法不同）
> 结论：合并为 `03-评审量表-v1.1-合并版.md`，此后**只有 v1.1 有效**

## 一、逐条对照

| 架构C 维度 | 架构H 对应 | 关系 | 处理 |
|---|---|---|---|

| 2 核心概念洞察力（身份≠私钥、迁移活vs迁移人） | 无 | **缺口** | 新增 D2（权重 11） |
| 3 应用场景与商业判断（能否变现、风险意识） | D2 定位（部分） | 缺口（架构H无独立维度，散在题目里） | 并入 D6 |
| 4 技术选型合理性（复用 vs 自建边界） | D2 定位 + D3 可行性 | 重叠 | 作为 D3 的显式锚点 |
| 5 财税法业务理解深度（风险指标、汇算、鉴证边界） | 无 | **缺口（结构性缺失）** | 新增 D6（权重 12） |

| 7 工程可落地性（分阶段、最小验证） | D3 可行性 + D8 最小下一步 | 完全重叠 | 合并为 D4 |

| 9 文档质量（清晰、结构化、可迭代） | 无 | 缺口（但需防"读起来专业"给分） | 新增 D9，**压到 4 分低权重** |

## 二、架构H 独有（架构C 没有的机制）

| 架构H 机制 | 架构C | 处理 |
|---|---|---|
| 事实核查维度（条文号/版本号必须给出处） | 无 | 合并进 D1，且保留为独立核对轮 |
| 反炒作维度（RAG已死/AI社会/代币） | 无 | 保留 D10 |
| **硬性否决项**（命中即 0 分） | 无 | 保留并扩到 7 条 |
| 分档判据（每维度给 5/3/1 锚点） | 只有"1–5 分"无锚点 | 保留，全部维度补齐锚点 |
| 加权总分（区分主次） | 等权平均 | 采用架构H加权 |

## 三、口径冲突（必须统一，否则分数不可比）

| 冲突 | 架构C | 架构H | 采纳 |
|---|---|---|---|
| 计分方式 | 每项 1–5 等权 | 8 维加权 100 | **加权 100**（否则"文档质量"与"身份架构"同权，会拉平关键差异） |
| 是否设否决 | 无 | 5 条 | **保留否决**（否则编造条文号也能拿高分） |
| 分档判据 | 无，只写"看什么" | 每维 5/3/1 锚点 | **保留分档**（否则评分随评审人宽严漂移） |
| 材料是否可只看摘要 | 必须通读原文 | 允许摘要（02 文件） | **必须通读原文**，摘要只用于定位（采纳架构C，这条更严） |

## 四、合并后净变化

- 维度：8 → **10**（新增：核心概念洞察力、业务与领域深度、文档质量）
- 权重重心：从"协议工程"偏向"**工程 + 业务**"各占一半（财税场景下这是对的）
- 否决项：5 → **7**（新增"无资质却承诺出正式鉴证文书"、"把未验证选型当已验证结论"）
- 反向吸收：**材料的通读要求**采纳架构C（更严）

## 五、一句话

架构C的表强在**业务与概念的判据**（懂财税、会抓关键矛盾），我的表强在**可操作性与防作弊**（分档、加权、否决、强制出处）。
合并后的 v1.1 = 用我的可操作性，装架构C的业务视角。
